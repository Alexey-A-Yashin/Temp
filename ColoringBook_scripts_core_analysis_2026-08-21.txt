ColoringBook — разбор ядра scripts/
================================================================================
Дата: 2026-08-21
Источник: ColoringBook (Claude).zip → ColoringBook/scripts/**/*.cs
Срез: 2026-08-11, 75 файлов .cs, ~12.4k строк / ~1.2 МБ исходников.

Важно: это НЕ архив с FluvialField 961×961 из ЗАМЕРЫ_И_ЗАДАЧА.md.
Здесь ядро — dual-mesh + AlpineTerrain + VegetationPlacer + LevelView3D +
Sketch. Если актуальный scripts ушёл дальше (fluvial field, кольца), часть
выводов по Mapgen устареет, слои Domain/Application/Presentation останутся
полезны как карта архитектуры.


================================================================================
1. СЛОИ (CLEAN-ISH ARCHITECTURE)
================================================================================

  Bootstrap/          — вход Godot (GameBootstrap : Node3D)
  Application/        — сценарии приложения (LevelService, SceneRouter, RiverWorld)
  Domain/             — чистые типы уровня, без Godot
  Infrastructure/     — генерация, растения, sketch I/O, persistence
  Presentation/       — экраны, LevelView3D, отладка

Соблюдение границ
  Domain:      Godot не импортируется — хорошо.
  Application: SceneRouter тянет Godot (UI-навигация) — приемлемо для тонкого слоя.
  Infrastructure.Generation (Mapgen, Plants): без Godot в генерации меша/высот —
               данные чистые; Presentation собирает Mesh/MultiMesh.
  Persistence/Sketch: FileAccess Godot — ожидаемо.

Контракт уровня
  ILevelGenerator.Generate(LevelDescriptor) → LevelData
  MapgenLevelGenerator — единственная боевая реализация (+ Stub).

Итог по слоям: каркас правильный для игры такого типа. Основной риск не в
«слои перемешаны», а в том, что тяжёлая логика сконцентрирована в 3–4 файлах.

3. ПОТОК ДАННЫХ (КАК УСТРОЕНО ЯДРО)
================================================================================

  GameBootstrap._Ready
    → GraphicsSettings, MapgenLevelGenerator, LevelService
    → LevelView3D, Camera, UI, SketchCapture, экраны
    → генерация / показ уровня

  MapgenLevelGenerator.Generate
    → MeshBuilder.Build (dual mesh, pointCount от качества)
    → AlpineTerrain.Generate (высоты, вода, склоны, каналы…)
    → VegetationPlacer (экземпляры по регионам)
    → LevelData (points, regions, vegetation)

  LevelView3D
    → строит меш рельефа, воду, MultiMesh растительности
    → LOD / impostor / камера / телеметрия (в более новых сборках — sweep T)

  SketchCapture
    → снимок viewport → контуры / слои для раскраски
    → Gallery / Painting screens

Река как мир: RiverWorld + ChunkCoord + RiverChunkGenerator / Spine / Meander —
задел непрерывного мира вдоль русла; LevelData уже несёт ChunkIndex, seams.


================================================================================
4. РАЗБОР ПО ПОДСИСТЕМАМ
================================================================================

4.1. Domain (~26 КБ)
--------------------
Сильные стороны:
  - Маленькие immutable-ish типы (MapPoint, VegetationInstance, ChunkCoord).
  - Enums биомов, растительности, сезона.
  - ILevelGenerator / ILevelSaveRepository / ISketchRepository — правильные порты.

Слабые:
  - Domain почти не выражает инварианты рельефа (пояса, уклоны, «нрав») —
    они живут в Infrastructure (TerrainParams) и Presentation.
  - При переходе на fluvial field контракт LevelData (points/regions dual-mesh)
    может стать узким местом: либо адаптер «grid → regions», либо эволюция
    LevelData.

Рекомендация: не раздувать Domain; при смене генератора — явный Anti-Corruption
слой Mapgen→LevelData, не протечка grid в UI.

4.2. Mapgen / AlpineTerrain
---------------------------
AlpineTerrain.Generate — монолит: долины, пики, edge massifs, spine, meanders,
oxbow, эрозия, гидрология, upstream.

Рядом:
  ConditionedErosion — Array.Sort(delegate) каждый шаг (дорого при росте n)
  HydraulicErosion   — капли
  Hydrology, MainChannel, Outlet, TerrainParams

Проблемы:
  - Сложно тестировать и профилировать куски.
  - List<int>[] upstream на регион — лишние аллокации; лучше CSR.
  - Параллельные модели эрозии (conditioned + hydraulic + позже fluvial) без
    одного «source of truth» высот.

Упрощение:
  BuildValleyGraph → StampRelief → RunErosion → BuildHydrology → PackResult
  Один выбранный erosion path в боевом режиме; остальное — #if DEBUG / bench.

4.3. Plants (~314 КБ)
---------------------
PlantGenerator.cs (~2691) + partials Cover/LSystem/SmallPlants + SCA/tree.

Сильные:
  - partial-файлы по темам (L-system, cover, small plants).
  - PlantSpecies / Catalog / Genome отделены от меша.

Слабые:
  - Основной PlantGenerator.cs всё ещё огромный (кроны, SCA, меши деревьев).
  - Метрики и генерация в одном пространстве имён — ок, но hot path мешей
    стоит держать без диагностических веток.

Для производительности игры важнее VegetationPlacer + LevelView3D MultiMesh
LOD, чем микрооптимизация L-system при одноразовой генерации прототипа.

4.4. VegetationPlacer (~746 строк)
----------------------------------
Связка «где что растёт» по регионам/биомам. Критичен для вида и плотности.
Должен оставаться чистым данными (список VegetationInstance), без Node.

Следить: фильтры тропы/скалы/воды, плотность cover vs деревья — это игровые
правила, их место здесь или в Domain-сервисе, не в LevelView3D.

4.5. LevelView3D (~4816 строк) — главный риск сопровождения
-----------------------------------------------------------
Типичный «god view»: террейн, вода, растительность, LOD, impostor, камера,
ввод, отладочная телеметрия.

Это нормально для прототипа Godot, но дальше файл будет ломаться на каждом
изменении.

Распил по ответственности (без смены поведения):

  LevelTerrainMeshBuilder     — массивы меша, юбки колец, UV
  LevelVegetationRenderer     — MultiMesh buckets, LOD sort
  LevelCameraController       — orbit / player eye
  LevelViewTelemetry          — T-sweep, JSON
  LevelView3D                 — тонкий фасад, wire-up

Даже частичный вынос Vegetation + Telemetry сильно упростит диффы.

4.6. GameBootstrap (~1696)
--------------------------
Смешивает:
  - DI/composition root (хорошо)
  - создание света/environment
  - UI labels / hotkeys
  - маршрутизацию sketch
  - возможно отладочные режимы

Упрощение: оставить composition + _Process/_Input делегирование;
свет/environment → LevelEnvironmentFactory; hotkeys → DebugInput 또는
InputMap actions.

4.7. SketchCapture (~941)
-------------------------
Ядро продукта (фото → контур → раскраска). Godot Image/Viewport — уместны.
Держать чистый pipeline: Capture → preprocess → edges → layers → save.
Не смешивать с генерацией гор.


================================================================================
5. ОПТИМИЗАЦИЯ (ПРАКТИЧЕСКИЕ РЫЧАГИ В ЭТОМ СРЕЗЕ)
================================================================================

Генерация (CPU, один раз на уровень/чанк)
  1. ConditionedErosion: radix/keys вместо Array.Sort(delegate).
  2. AlpineTerrain: убрать new List на регион в hot paths; CSR neighbors.
  3. Не гонять Hydraulic + Conditioned + лишние smooth, если профиль не просит.
  4. Кэш PlantMeshData по (kind, variant, genome-hash) — прототипы деревьев
     не пересобирать каждый чанк.

Кадр (GPU/CPU каждый кадр) — LevelView3D
  1. LOD/impostor пороги и cover_hide — главный рычаг FPS.
  2. MultiMesh instance count vs visible tris — уже логировались в sweep.
  3. Не обновлять SortChunk/LOD чаще, чем нужно (гистерезис дистанций).

Память
  1. Пулы буферов эрозии.
  2. Не держать дубли height arrays после Build.

    Params напрямую — связь удобная, но жёсткая).

================================================================================
9. ИТОГ
================================================================================

Ядро scripts/ — это layered C# проект с тонким Domain и толстым
Infrastructure + Presentation. Архитектурный каркас здоровый.

Реальная сложность сосредоточена в четырёх точках:

  1) LevelView3D          — распилить
  2) PlantGenerator       — уже partial, ядро всё ещё тяжёлое
  3) AlpineTerrain        — монолит генерации рельефа (в этом срезе)
  4) GameBootstrap        — composition + UI + input в одном Node

Оптимизация кадра: LOD/растительность в Presentation.
Оптимизация генерации: сортировки/аллокации в Mapgen; стратегически —
один алгоритм высот и не считать 905×961 без multigrid/прокси (см. отдельные
разборы рельефа).

Для анализа актуального fluvial-ядра нужна повторная выкладка scripts с
FluvialField.cs / RidgedMountains.cs / LevelAudit.cs.
