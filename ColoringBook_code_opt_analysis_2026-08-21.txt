================================================================================
1. КАРТИНА УЗКИХ МЕСТ (ПО ЗАМЕРАМ)
================================================================================

Сетка 961×961, 905 шагов, ~205 с, ~линейно по числу ячеек.

Внутри шага доминируют:
  • заливка впадин (priority queue)  — порядка секунды на шаг на 961
  • сортировка                       — при сравнении ~900 мс; radix уже есть

Отвергнуто замерами: редкая заливка, урезание числа шагов, перенос настроек
с мелкой сетки на крупную.

Следствие для кода: микрооптимизации layout дадут проценты; порядок величины
меняется только сменой постановки счёта (multigrid, прокси для sweep) или
существенным ускорением fill.


================================================================================
2. ЧТО ВИДНО В ДОСТУПНОМ КОДЕ MAPGEN
================================================================================

2.1. ConditionedErosion.cs — прямой аналог «дорогого шага»
----------------------------------------------------------
Каждая итерация:

  order[r] = r;
  Array.Sort(order, (a, b) => f[b].CompareTo(f[a]));  // делегат, n·log n вызовов

Это тот же класс проблем, что уже лечили поразрядной сортировкой в поле
поднятия/эрозии. На графе регионов n меньше 961², поэтому боль не 205 с, но
паттерн вредный.

Рекомендация (если этот путь ещё вызывается):
  • radix / sorted indices по ключу filled[r] без делегата;
  • буферы downslope/area/order — поля класса или пул, не new на каждый Apply,
    если Apply зовётся часто.

Барьерный врез при drop<=0 (резать по filled) — логика осмысленная, не трогать
без сверки озёр.

2.2. HydraulicErosion.cs — капли
--------------------------------
Классический particle-based проход: O(droplets × iterations). Параллелить
капли можно (у каждой свой след), но нужны либо атомики в Change, либо
thread-local delta + merge. Имеет смысл только если профиль покажет, что
HydraulicErosion заметна рядом с fluvial-полем; иначе не приоритет.

Thermal Apply: delta[] на весь height — нормально; двойной цикл 3×3 —
кандидаты на параллель по строкам.

2.3. AlpineTerrain.cs — «бог-объект» (~1700 строк)
-------------------------------------------------
Generate() тянет:
  долины, пики, edge massifs, spine реки, meander hills, oxbow, эрозию,
  гидрологию, upstream lists, main channel, outlet…

Проблемы упрощения (не только скорости):

  a) Один метод Generate с десятками локальных массивов и ветвлений —
     сложно тестировать и профилировать куски.
  b) List<int>[] upstream = new List на каждый регион — аллокации и cache miss;
     для графа фиксированной степени лучше CSR (offsets + flat neighbors).
  c) Множество SeededRandom с магическими XOR-константами — воспроизводимо, но
     шумно для чтения; вынести фабрику RNG по подсистемам.
  d) Флаг ErosionEnabled константой — ок для A/B, но путь «без эрозии» всё равно
     тащит подготовку данных вокруг.

Упрощение структуры (без смены внешнего Result):

  AlpineTerrain.Generate
    → BuildValleyGraph(...)
    → StampMassifs(...)
    → ApplyRiverSpine(...)
    → RunErosion(...)
    → BuildHydrology(...)
    → PackResult(...)

Каждый этап — отдельный файл/класс с чистыми входами-выходами (массивы +
settings). Тогда профилирование и вырезание мёртвых веток дешевле.


================================================================================
3. ЦЕЛЕВОЙ FLUVIAL-КОНТУР (ПО ДОКУМЕНТУ) — ОПТИМИЗАЦИЯ
================================================================================

Псевдокод шага:

  h += U
  surf = FillDepressions(h)     // priority queue
  order = RadixSortByHeight
  flow accumulation
  h -= K * sqrt(area) * slope
  h += D * laplacian

3.1. Обязательные проверки в FluvialField / RidgedMountains (когда будет файл)
------------------------------------------------------------------------------
  [ ] U(x,y) считается один раз до цикла 905, не внутри
  [ ] Все буферы (h, surf, flow, order, receivers, heap storage) — без new
      на каждый шаг
  [ ] Radix действительно используется на боевом пути 961 (не только в bench)
  [ ] FillDepressions не захватывает замыкания Push/Pop на каждый вызов
      (ранее на 241 это не дало CPU, но на 905×961 стабильность GC важна)
  [ ] Граница (базис эрозии) не попадает в кучу лишний раз / обрабатывается
      единообразно

3.2. Упрощение логики шага
--------------------------
Сейчас шесть стадий. Имеет смысл явно разделить:

  struct StepBuffers { float[] H, Surf, Flow, Area; int[] Order, Recv; ... }

  void Step(StepBuffers b, TerrainCharacter c) {
    Uplift(b, c);
    Fill(b);
    Sort(b);
    Route(b);
    Incise(b, c);
    Diffuse(b, c);
  }

Так проще вставлять профильные таймеры и выключать стадии в bench.

3.3. Parallel.For — только безопасные стадии
--------------------------------------------
Безопасно без смены семантики:
  • uplift по ячейкам
  • laplacian (с double-buffer)
  • incision при уже посчитанных area/slope/recv

Не параллелить «в лоб»:
  • priority-flood
  • накопление стока вниз по дереву без топологической декомпозиции

3.4. Multigrid как упрощение постановки, не «ещё флаги в шаге»
--------------------------------------------------------------
Грубая полная эволюция + upsample + короткий догон на 961 — отдельный
pipeline-режим GenerateCoarseThenRefine(...), а не ветвление внутри каждого
из 905 шагов. Иначе код станет ещё запутаннее.

4. ПОДБОР ПАРАМЕТРОВ (КОД BENCH)
================================================================================

Документ: Parallel.For по сочетаниям уже есть; на 1 ядре бесполезен.

Упростить и ускорить подбор:

  1) Ключ кэша: (seed, characterHash, gridSize, algoVersion) → метрики + поле
  2) Двухфазный evaluator:
       cheap = Run(481) → score
       if score в топ-K: Run(961) → official score
  3) Не хранить полные 961 float в кэше, если нужны только 20 метрик —
     экономия диска/RAM при сотнях прогонов
  4) TerrainCharacter: явные ranges + дискретизация для sweep (не «плавающие»
     10 непрерывных осей сразу)

================================================================================
9. КРАТКИЙ ИТОГ
================================================================================

В доступном коде главный запах — ConditionedErosion с Array.Sort(delegate)
каждый шаг и монолит AlpineTerrain. Для текущей боли 205 с это вторично
относительно fluvial 961.

По алгоритму из ЗАМЕРЫ: код шага упрощать до явных стадий и буферов без
аллокаций; ускорение порядка величины — multigrid и организация подбора,
а не новый Priority-Flood. Распараллеливание — точечно на независимых
стадиях. Архитектурно — один источник высот, вычищение параллельных
генераторов рельефа.
