ColoringBook — ускорение поля 961×961 (905 шагов): разбор задачи

Дата: 2026-08-21
Основание: ЗАМЕРЫ_И_ЗАДАЧА.md + архив проекта (код не прогонялся в этой сессии

Территория 115.2 км, сетка 961×961 (ячейка 120 м), ~923k ячеек.
Модель: stream power + uplift + depression fill + flow routing + diffusion.
905 шагов, один поток. Полное поле ~205 с.


================================================================================
1. ЧТО УЖЕ ДОКАЗАНО ЗАМЕРАМИ (не повторять)
================================================================================

1.1. Время ~линейно по числу ячеек (~220 мкс/ячейка на всё построение).
     Узкие места внутри шага: заливка впадин и (при сравнении) сортировка.
     Поразрядная сортировка уже есть — правильно.

1.2. Редкая заливка (каждые N шагов) ускоряет, но портит качество:
     устаревший filled surface ломает направления стока. Не использовать
     как «просто N=4» без другой модели устойчивости.

1.3. Меньше итераций (200/400 вместо 905) не даёт того же качества:
     процесс не выходит на плато по метрике долгов. Резать N «вслепую» нельзя.

1.4. Настройки с мелкой сетки на крупную не переносятся
     (38 км vs 115 км: высота, уклон, число нарушений).
     Подбор только на 241/481 недостаточен для финальных 961.

1.5. Parallel.For по РАЗНЫМ наборам параметров — верный ход для sweep;
     на одноядерной машине выигрыша нет. Это не ускоряет один прогон 961.


================================================================================
2. ПЕРЕСОСТАВЛЕНИЕ ЗАДАЧИ
================================================================================

Две разные цели, их нельзя смешивать:

  A) Подбор параметров (десятки–сотни полных прогонов)
  B) Один «боевой» прогон 961×961 при запуске игры

Ускорение A важнее для текущей боли («час на 16 сочетаний»).
Ускорение B — для игрока (205 с на старте неприемлемо).

Многие приёмы хороши для A и неприемлемы для B, и наоборот.


================================================================================
3. СТРАТЕГИЯ ДЛЯ ПОДБОРА ПАРАМЕТРОВ (A)
================================================================================

3.1. Прокси-метрика на средней сетке + редкая валидация на 961
------------------------------------------------------------------
Хотя «настройка с 38 км не переносится один в один», часто сохраняется
*ранжирование* кандидатов: набор, лучший на 481, с высокой вероятностью
лучше среднего и на 961.

Схема:
  - основной sweep на 481×481 (или 361), 905 шагов или урезанный N, если
    ранжирование стабильно;
  - топ-K (3–5) наборов — полный 961;
  - зафиксировать корреляцию рангов 481↔961 на 20–30 случайных наборах.
    Если Spearman высок — подбор на 481 законен; если нет — только 961.

Это не «перенос чисел», а «перенос порядка предпочтений».

3.2. Многоуровневый sweep, а не полный факториал на 961
------------------------------------------------------------------
  1) Грубая сетка параметров на 241 (быстро) → отсев явного мусора.
  2) Уточнение на 481.
  3) Финал на 961 только для победителей.

3.3. Не оптимизировать все 10 величин сразу
------------------------------------------------------------------
Раз параметры почти независимы по рычагам (из более ранних замеров проекта),
но правка по одной ломает другое — использовать блоки:
  - блок тектоники (U, разброс, период, перекос)
  - блок эрозии (K, D, пороги воды)
  - N шагов отдельно, если метрика сходится медленно
Покоординатный спуск / Bayesian optimization по дешёвой прокси (481).

3.4. Параллельный sweep на многоядерной машине
------------------------------------------------------------------
Уже сделано в tools/bench — перенести прогон на машину с 8–16 ядрами:
16 сочетаний ≈ время одного, а не ×16.

3.5. Кэш поля по ключу (seed + character + algoVersion) — только для A/отладки
------------------------------------------------------------------
В игровом клиенте вы сознательно кэш отключили. Для bench-подбора кэш
прогонов обязателен: повтор того же набора не должен стоить 205 с.


================================================================================
4. УСКОРЕНИЕ ОДНОГО ПРОГОНА 961 (B) БЕЗ ПОТЕРИ КАЧЕСТВА
================================================================================

4.1. Многосеточность (самый перспективный из непробованных)
------------------------------------------------------------------
Идея: большая часть формы водосбора рождается на крупных масштабах.

Вариант «продолжить, не перезапускать»:
  1) 905 шагов на 241 (или 481) → полный цикл эволюции.
  2) Bilinear/bicubic upsample высоты на 961.
  3) Дополнительные M шагов на 961 (M << 905), с тем же U/K/D,
     чтобы врез и сток «прорезали» масштаб 120 м.

Риск: сеть стока на мелкой сетке не совпадёт с «истинной» 905×961.
Проверка: те же 20 метрик LevelAudit + % совпадения русел / пороги поясов
на 3+ сидах. Если M=80…200 даёт долги ≈ полного 905 — это главный выигрыш
(порядок: минуты → десятки секунд).

Важно: не путать с «редкой заливкой на одной сетке» — там ломался сток
внутри одной дискретизации; здесь сток на каждом уровне считается заново
на своей сетке.

4.2. Инкрементальная / локальная заливка впадин
------------------------------------------------------------------
Полный Priority-Flood каждый шаг — O(n log n) доминирует.

Имеет смысл исследовать (нужен замер и сверка):
  a) После шага 1 пересчитывать flood только если max|Δh| или объём
     изменения выше порога; иначе — прежние receivers (ОСТОРОЖНО:
     близко к отвергнутой редкой заливке; порог и «полный flood каждые
     K» вместе).
  b) Алгоритмы incremental depression filling в литературе DEM
     (обновление кучи только в затронутых бассейнах). Сложнее в коде;
     выигрыш на 961 может быть заметным, если Δh локален.
  c) На поздних шагах, когда рельеф «созрел», впадин мало — адаптивно
     упрощать (если объём заливки < ε, короткий путь). Только с контролем
     метрики долгов.

Без сверки качества (как в §4.1 документа) не внедрять.

4.3. Распараллеливание внутри шага
------------------------------------------------------------------
Последовательность uplift → fill → sort → flow → incision → diffuse
по шагам строго последовательна.

Внутри шага:
  - uplift, diffuse (лапласиан): идеально parallel for по ячейкам;
  - incision при известных area/slope: parallel;
  - fill (priority queue): плохо параллелится классически;
  - flow accumulation down trees: возможны параллельные проходы по
    независимым поддеревьям после топосортировки — выигрыш средний,
    сложность высокая.

Практичный минимум: Parallel.For на uplift + laplacian + (после fill)
incision. На 8 ядрах часть шага, не fill, может дать 1.3–2× на эти
фазы; общий прогон упрётся в fill+sort.

4.4. GPU
------------------------------------------------------------------
Решётка uplift/diffuse/incision — да.
Priority-Flood / heap — на GPU неудобны; есть research-реализации
parallel depression filling, но это отдельный R&D, не быстрый патч.

Имеет смысл только если CPU-многосетка и parallel for исчерпаны, а 961
остаётся >30–40 с.

4.5. Данные и константы внутри цикла
------------------------------------------------------------------
  - uplift(x,y) один раз до цикла (если поле U статично).
  - Горячие массивы float32, без аллокаций на шаг (у вас частично уже так).
  - Индексы int в куче.
  - Не ждать «вдвое» только от layout на 923k — проценты, не порядок.

================================================================================
8. ОТВЕТ НА ВОПРОС ДОКУМЕНТА
================================================================================

«Как ускорить 961×961 при 905 шагах, не теряя качества?»

  1) Для подбора — не ускорять один 961, а считать большинство попыток на
     481 с проверкой рангов и финалом на 961; плюс много ядер.
  2) Для боевого поля — в первую очередь multigrid (грубая полная эволюция
     + короткий догон на 961), со сверкой LevelAudit; не редкая заливка
     на одной сетке.
  3) Parallel внутри шага — на безопасных стадиях; fill оставить
     последовательным, пока не будет измеримого инкрементального алгоритма.
  4) GPU — запасной путь после (2).

Качество «не терять» = те же 20 замеров и сумма долгов в пределах вашей
нормы на нескольких сидах, а не один уклон.
