# ТЕСТОВЫЙ СТЕНД: ПОЛНЫЙ ПОРЯДОК РАБОТЫ

ColoringBook, составлено 2026-08-16 при состоянии V297.

Документ описывает весь путь: что и откуда ставится, как данные попадают в
стенд, что снимается на выходе.

---

# 0. ЗАЧЕМ СТЕНД СУЩЕСТВУЕТ

Godot в контейнере не собирается и не запускается. Без стенда любая правка
проверялась бы только прогоном у пользователя — а это часы на круг.

Стенд решает три задачи:

| задача | чем |
|---|---|
| поймать ошибку сборки до выдачи архива | `godotcheck` + четыре проверки |
| померить рельеф, кадры, растительность | `gentest` |
| **увидеть** результат картинкой | `gentest/Render.cs` |

Это возможно потому, что слои `Domain` и `Infrastructure/Generation` **намеренно
не зависят от Godot**. Держать эту независимость — правило проекта: как только
генерация начнёт звать движок, стенд умрёт.

# 1. УСТАНОВКА

## 1.1. Что нужно в системе

```
.NET SDK 8.0        проверить: dotnet --version
python3             для проверить_скобки.py и для сборки картинок
```

Больше ничего. Ни Godot, ни NuGet-пакетов, ни внешних библиотек: отрисовка PNG

Из архива `стенд.tar.gz`, приложенного к передаче дел.

cd ~/bench
```

После распаковки должно быть:

```
gentest/            замеры и картинки
godotcheck/         проверка сборки
nuget.config        ОБЯЗАТЕЛЕН: без него сборка лезет в сеть и падает

проверить_вызовы.sh
проверить_using.sh
проверить_методы.sh
проверить_скобки.py
```

## 1.3. Откуда берётся код проекта

Из архива проекта, который присылает пользователь. Распаковать куда угодно,
например `~/proj/ColoringBook`. Путь к нему передаётся стенду доводом.

## 1.4. Проверка, что установка удалась

```

# 2. КАК ДАННЫЕ ПОПАДАЮТ В СТЕНД

## 2.1. Главное: стенд собирается из КОПИЙ, а не из проекта

`подготовить.sh` копирует исходники в каталоги `src/` внутри стендов.

**Зачем копии, а не сборка из проекта напрямую.** Во-первых, видно, что именно
проверялось. Во-вторых, случайная правка стенда не уйдёт в игру.

**Цена копий — расхождение.** Один стенд (`routes`) забыли вписать в скрипт, и
его копия три дня оставалась кодом трёхнедельной давности. Прототип и проект
считали разный рельеф, и сверка не сходилась.

**Отсюда правило: запускать `подготовить.sh` ПОСЛЕ КАЖДОЙ правки в проекте.**
Забыл — меришь старый код.

## 2.2. Что именно копируется

```
                          gentest    godotcheck
Domain/                      +           +
Infrastructure/Generation/   +           +
  кроме Generation/Plants    —           —     зависит от Godot
Presentation/Level/
  TerrainMetrics.cs          +           +
  FarBackground.cs           —           +
  RiverRibbon.cs             —           +
  TerrainReport.cs           —           +
  SeasonColorMapper.cs       —           +
  TerrainGradient.cs         —           +
Presentation/Diagnostics/
  SessionLog.cs              —           +
```

`gentest` берёт только то, что от Godot не зависит: он **исполняется**, а не
только собирается.

`godotcheck` берёт ещё и слой представления — он его **собирает по заглушкам**,
чтобы поймать ошибки, но не исполняет.

## 2.3. Что подменяется заглушками

```
GodotStubs.cs        типы Godot: Vector3, Mesh, Node3D, MultiMesh и прочие
LevelView3DStub.cs   пишется скриптом на лету, три поля
```

**`LevelView3D.cs` и `GameBootstrap.cs` НЕ СОБИРАЮТСЯ.** Это 5800 и 2000 строк,
завязанных на десятки систем движка. Попытка собрать настоящий `LevelView3D` была
и отвергнута: не хватило шести типов, добавил, затем вылезли окна просмотра,
сервер отрисовки, сигналы. Дописывать их — значит поддерживать копию движка,
которая разойдётся молча.

**Следствие: ошибки внутри этих двух файлов проходят насквозь.** Для этого и
нужны четыре проверки из раздела 3.

## 2.4. Как задаются исходные данные для замера

Стенд не принимает никаких файлов. Всё строится из **сида** — то же, что в игре:

```csharp
var ch = TerrainCharacter.ForSeed(42);            // нрав местности
var f  = FluvialField.Build(481, ext, 42, ch);    // поле
var r  = Ringgen.Build(42, lift, out var flow);   // кольца
```

`Ringgen.cs` — **копия построения колец без Godot**. Это второй источник правды,
и он может разойтись с игрой. Признак расхождения: числа стенда не сходятся с
числами из журнала игры. Такое было (расстановка 15 мс против 65 850) и всегда
означало разницу в самих стендах, а не в данных.

# 3. ЧЕТЫРЕ ПРОВЕРКИ ПЕРЕД ВЫДАЧЕЙ АРХИВА

Запускать **все четыре, каждый раз**. Пропуск любой стоил ошибки сборки у
пользователя; за два дня — восемь раз.

```
sh проверить_вызовы.sh  ~/proj/ColoringBook
sh проверить_using.sh   ~/proj/ColoringBook
sh проверить_методы.sh  ~/proj/ColoringBook
python3 проверить_скобки.py ~/proj/ColoringBook
```

Ожидаемый вывод каждой — `готово` без строк выше.

## 3.1. Что ловит каждая

| проверка | что сверяет | какую ошибку поймала |
|---|---|---|
| `проверить_вызовы` | методы между слоями по трём парам полей | `SetStemMarkersVisible` удалён, а вызовы остались |
| `проверить_using` | объявления пространств имён; типы библиотеки (`List`, `Stack`…); ссылки на несуществующие типы | `RingVegetationPlacer` без `using`; `MapgenLevelGenerator` после удаления |
| `проверить_методы` | вызовы вида `Тип.Метод(` | `SeasonState.ForMode` — метод выдуман |
| `проверить_скобки` | равновесие скобок; `else` без `if` | `else` остался после вырезки `if` |

## 3.2. Что проверками НЕ ловится

Остаётся за сборкой в самом Godot:

- **неверное имя поля** — `start.Z` у `Vector2`, где составляющие X и Y;
- **вызов удалённого метода внутри файла** — не отличить от довода-функции:
  `Func<int,bool> same` вызывается как `same(j)`.

Вторую проверку я писал и **отверг**: два ложных срабатывания при нуле пойманных
настоящих. Молчащая проверка хуже отсутствующей, кричащая зря — тем более.

## 3.3. Правило о самих проверках

**Каждая новая проверка проверяется на настоящей ошибке.** Порядок: вносишь
ошибку во временную копию проекта, убеждаешься, что проверка её нашла, копию
удаляешь.

```
rm -rf /tmp/tp && cp -r ~/proj/ColoringBook /tmp/tp
# внести ошибку в /tmp/tp
sh проверить_чтото.sh /tmp/tp     # должна найти
rm -rf /tmp/tp
```

Дважды проверки молчали на том, ради чего заводились, и это обнаруживалось
только так.

# 4. КАК ПИСАТЬ ЗАМЕР

`gentest/Program.cs` — **рабочее место, а не готовая программа**. Переписывается
целиком под каждую задачу.

## 4.1. Заготовка

```csharp
using System;
using System.Collections.Generic;
using Bench;
using ColoringBook.Domain.Level;
using ColoringBook.Infrastructure.Generation;
using ColoringBook.Infrastructure.Generation.Mapgen.Algorithms;

class Program
{
    static void Main()
    {
        int n = Ringgen.RingResolution;
        float ext = Ringgen.OuterExtent;
        var ch = TerrainCharacter.ForSeed(42);
        var f = FluvialField.Build(481, ext, 42, ch);

        // смещение по высоте: дно долины на 1000 м, как в игре
        float lo = 1e9f; foreach (var v in f) if (v < lo) lo = v;
        var r = Ringgen.Build(42, 100f - lo, out var flow);

        // высота в мировой точке
        float H(float wx, float wz)
        {
            foreach (var rr in r)
                if (MathF.Abs(wx) < rr.Half && MathF.Abs(wz) < rr.Half)
                    return Ringgen.SampleGrid(rr.H, n, rr.Half, rr.Step, wx, wz);
            var last = r[^1];
            return Ringgen.SampleGrid(last.H, n, last.Half, last.Step, wx, wz);
        }

        // ... замер ...
    }
}
```

## 4.2. Обязательное правило замера

**Мерить всегда ДО и ПОСЛЕ, в одном прогоне, на нескольких сидах.**

```csharp
foreach (int seed in new[] { 42, 1055, 777 })
```

Один сид обманывает: величина, снятая на глаз с одного мира, ломается при смене
миров — это случалось.

## 4.3. Пояса покрова: главная ловушка

Пороги поясов — **квантили по территории**, а не числа. Взять наугад — получить
враньё вдесятеро (случалось: замер показал «вокруг только кустарник», а там было
17 649 растений).

```csharp
float rl = 1e9f, rh = -1e9f;
foreach (var rr in r) foreach (var v in rr.H) { if (v<rl) rl=v; if (v>rh) rh=v; }
var all = new List<float>();
foreach (var rr in r) for (int k = 0; k < rr.H.Length; k += 3) all.Add(rr.H[k]);
all.Sort();
float Q(double q) => (all[(int)(all.Count * q)] - rl) / (rh - rl);
float qf = Q(0.30), qs = Q(0.62), qa = Q(0.72), qr = Q(0.82);
```

**Лучше свериться со строкой `[пояса]` из журнала игры** — там настоящие.

# 5. ЧТО СНИМАЕТСЯ НА ВЫХОДЕ

Три группы мер. Первые две — числа, третья — картинки.

## 5.1. Правдоподобие рельефа (`TerrainMetrics`, из проекта)

```csharp
var g = TerrainMetrics.Geomorphons(h, side, cell, radius: 4);
double dev = TerrainMetrics.GeomorphonDeviation(g);
var (ratio, orders) = TerrainMetrics.HortonRatio(filled, side, minFlow);
var (bias, diag) = TerrainMetrics.AspectBias(h, side, cell);
var (pits, spikes, _, _) = TerrainMetrics.PitsAndSpikes(h, side, cellM, thr);
```

| мера | что значит | цель | сейчас |
|---|---|---|---|
| отклонение геоморфонов | сумма расхождений долей девяти форм с природными | 0 | 14.7–21.3 |
| отношение Хортона | число русел соседних порядков | 3–5 | 4.2–4.5 |
| перекос направлений | равномерность склонов по румбам | 1.00x | зависит от ячейки |
| ямы и шипы | узлы, отличные от всех соседей | 0 | 0 ям |

Природное распределение форм для гор:

```
вершина 2, гребень 8, плечо 10, отрог 15, склон 38,
лощина 15, подножие 8, долина 4, яма 0
```

**ОБЯЗАТЕЛЬНО указывать радиус измерения.** При радиусе 4 отклонение 17.6, при
12 — 24.9 на одном и том же рельефе. Сравнивать можно только при одинаковом.

## 5.2. Красота и пригодность кадра

### Красота (`ViewAudit.cs`)

```csharp
var fr = ViewAudit.Shoot(H, isWater, camX, camZ, eyeAbove, yawDeg,
                         w: 48, h: 27, maxDist: 600f, beltAt);
```

| поле | что значит | годно |
|---|---|---|
| `SkyFraction` | доля неба | 0.15–0.60 |
| `DepthLayers` | сколько дальностных полос занято | ≥ 4 |
| `WaterVisible` | видна ли вода | желательно |
| `EdgeVisible` | видна ли кромка пояса | 77–98% кадров |
| `UprightFraction` | доля вертикалей | у нас была 0.0 |

**Число лучей и дальность влияют на ответ.** При 24 лучах и 2.5 км — 12% годных,
при 64 и 6 км — 50% на той же точке. Дальше 6 км ничего не меняется.

### Пригодность к раскраске (`Paintable.cs`)

```csharp
Render.EyeView(H, "/tmp/x.png", cx, cz, yaw, 320, 180, eye, dist);
var res = Paintable.Analyse(Render.LastLuma, Render.LastW, Render.LastH,
                            levels: 3, blurPasses: 2);
```

| поле | цель по живописи | у нас было |
|---|---|---|
| `Regions` | 7–15 (медиана 10) | 2.5–3.7 |
| `LargestShare` | ~0.29 | 0.48–0.60 |
| `ClutterShare` | ~0.13 | 0.00–0.02 |

Цели измерены по 60 репродукциям из Macpherson и Szabo. Приём: свести кадр к
трём тонам («чёрно-белый план» Macpherson), предварительно размыв («прищур»
Szabo), посчитать связные пятна.

### Растительность (`PlantProxy.cs`)

```csharp
var idx = new PlantProxy.Index(plants);
float WithPlants(float wx, float wz)
{
    float g = Bare(wx, wz); float t = idx.TopAt(wx, wz);
    return t > g ? t : g;
}
```

Конус для хвойного, купол для прочего. **Размеры взяты из игры, не выдуманы:**
сосна 28 м, пихта 31, лиственное 25, кустарник 11; полуширина кроны 2.7, 2.6,
3.4, 0.9.

Проверять: сколько висит в воздухе, сколько утонуло, какова сомкнутость полога
(природная 60–90%).

## 5.3. Картинки (`Render.cs`)

```csharp
Render.HeightMap(h, side, cellM, "/home/claude/work/x.png", "подпись");
Render.EyeView(H, "…/y.png", camX, camZ, yawDeg, w, hgt, eyeAbove, maxDist);
RenderOblique.Oblique(H, "…/z.png", cx, cz, span, pitchDeg, yawDeg, w, hgt);
```

PNG пишется без внешних библиотек. После `EyeView` доступны `Render.LastLuma`,
`LastW`, `LastH` — для разбора пригодности к раскраске.

**Правило: если результат можно изобразить — изобразить.** Отрисовщик нашёл
вертикальные пластины юбки, диагональную разлиновку и «песчаные дюны» — ничего
из этого числа не показывали.

Смотреть картинку через `view`, а сравнения собирать в один лист через PIL.

# 7. ПРИЗНАКИ ТОГО, ЧТО СТЕНД ВРЁТ

Тринадцать случаев за проект. Как узнавать:

**Стенд и игра расходятся на порядки** → разница в них самих, а не в данных.
Расстановка растений: 15 мс на стенде, 65 850 в игре. Оказалось, в игре пояс на
каждом вызове перебирал всё поле.

**Мера растёт, а картинка портится** → мера меряет не то. «Смены знака склона»
считали любую рябь; заменено на геоморфоны.

**Мера меняется от настроек замера** → сравнивать можно только при одинаковых.
Перекос направлений: 1.37x при ячейке 480 м и 4.04x при 15 м на ОДНОМ рельефе.

**Числа хорошие, а пользователь показывает негодный снимок** → мера неполна.
Осаждение дало 43% красивых кадров при рельефе из песчаных дюн: мера красоты не
следила за тем, остались ли горы горами.

**Проверка молчит на том, ради чего заведена** → проверить её на настоящей
ошибке. Случалось дважды.

# 8. ЧЕГО СТЕНД НЕ УМЕЕТ

Честный список — чтобы не тратить время на попытки.

| не умеет | чем закрывается |
|---|---|
| собирать `LevelView3D` и `GameBootstrap` | четыре проверки + сборка в Godot |
| проверять шейдеры | только Godot |
| мерить кадры в секунду и память | только устройство |
| показывать игру в движении | только пользователь |
| рисовать настоящие растения | подобия из простых тел |
| собирать под Android | только Godot с Android SDK |

**Два класса ошибок принципиально остаются за Godot:** неверные имена полей и
вызовы удалённых методов внутри файла.
