# ЧАСТЬ 1. ЧТО МЫ ДЕЛАЕМ И ЗАЧЕМ

## 1.1. Игра

Мобильная созерцательная игра в Godot 4.7 на C#. Две механики:

**Прогулки** по альпийской местности с трёх высотных уровней — сплав по реке,
велосипед по склону, полёт на воздушном шаре. Игрок фотографирует виды.

**Раскраска** снятых фотографий. На ней строится монетизация.

**Прогулки ПРОДАЮТ раскраску.** Это соотношение задаёт всё остальное.

## 1.2. Цель генератора, сформулированная точно

> Наибольшая плотность КРАСИВЫХ ВИДОВ на единицу площади, сразу с трёх уровней.

Это **не** «правдоподобный рельеф» и **не** «красивый рельеф». Горы, реки,
поляны, растительность — средства, а не цель.

## 1.3. Двойная мера кадра

Кадр должен быть **красивым** и **пригодным для раскраски**. Это разные вещи, и
они расходятся.

```
КРАСОТА                          ПРИГОДНОСТЬ К РАСКРАСКЕ
три плана (ближний, средний,     число связных пятен после
  дальний)                         сведения к трём тонам
средняя открытость: неба         размер крупнейшего пятна
  15-60%                         доля «сора» — пятен мельче
видимость воды                     сотой доли кадра
кромки поясов
слои глубины (не менее 4)
```

**Целевые числа взяты из 60 репродукций** живописи (Macpherson, Szabo):

```
пятен          медиана 10, четверти 7..15, размах 3..22
крупнейшее     29% кадра
сор            13%
```

## 1.4. Главный вывод об устройстве работы

**Игрок видит один процент территории.**

```
территория                3318 км²
русел                      183 км
игрок за сессию            1.2 км
ВИДНО с этого отрезка        35 км² = 1.06%
```

Отсюда:

- считать подробно надо **коридор**, а не всю площадь;
- мерить надо **вдоль маршрута**, а не по территории;
- искать надо не «как сделать хорошим весь рельеф», а **где хорошие места и как
  провести через них игрока**;
- можно идти **от кадра к рельефу**: мы знаем, где будет камера и куда посмотрит.

**Порядок работ из этого:** рельеф → **маршруты** → старт в точке маршрута →
растительность. Маршруты не последние, а вторые: они задают, где нужно качество.

# ЧАСТЬ 2. ТЕКУЩЕЕ СОСТОЯНИЕ

## 2.1. Конвейер построения уровня

```
1.  нрав местности от сида (TerrainCharacter)
2.  поле поднятия и эрозии, два уровня: 241 -> 481 (FluvialField)
3.  окно уточнения вокруг игрока, 4.8 км, ячейка 30 м (DetailTile)
4.  дренаж по полю (RidgedMountains.BuildDrainage)
5.  выбор точки старта по качеству вида (FarBackground.FindStartPosition)
6.  пять колец: 30/60/120/240/480 м (FarBackground)
7.  врезка русел, засыпка ям
8.  пороги поясов квантилями по территории
9.  покров и цвет
10. меш, юбка 50 м, нормали от функции высоты
11. растительность (RingVegetationPlacer)
```

## 2.2. Числа на V297

```
построение уровня        ~55 с (поле 44 с, окно 6 с)
растительность           11436 штук за 41 мс, узлов MultiMesh ~750
дно долины               1000 м, вершины ~4470 м
отклонение форм поля     14.7-21.3 (лучшее за проект)
отношение Хортона        4.2-4.5 при природных 3-5
кадры                    60 при 3 мс, память видеокарты 216 МБ
```

## 2.3. Что работает

- рельеф из процесса поднятия и эрозии, досчитанный до установившегося состояния;
- перелив вскрывает замкнутые впадины;
- осаждение наносов даёт плоское дно долин;
- растительность на уровне (впервые с V289);
- обход уровня с оценкой кадров по обеим мерам;
- запуск на Android проверен: **работает**.

## 2.4. Что НЕ сделано

- **маршруты** — самое важное, см. 1.4;
- вода рисуется покровом, ложе не врезано;
- сплав отключён: он шёл по руслу старого генератора;
- шар даёт 0% годных кадров — нет ближнего плана;
- палитра в RGB, не в перцептивном пространстве;
- раскраска: механика есть, но я её ни разу не видел.

# ЧАСТЬ 3. ТЕСТОВЫЙ СТЕНД

## 3.1. Зачем он

Godot собирать в контейнере нельзя. Стенд — это два проекта на чистом .NET,
которые собирают код проекта БЕЗ движка и позволяют мерить и рисовать.

**Правило: стенд только на .NET, без Python.** Питоновская копия — это вторая
реализация той же величины, а такие копии расходятся молча. Пять случаев в
разделе 10.2 файла решений.

## 3.2. Развёртывание

```
tar xf стенд.tar.gz -C ~/bench          # или распаковать архив
cd ~/bench
sh подготовить.sh <путь к проекту>       # копирует исходники в оба стенда
cd godotcheck && dotnet build            # проверка сборки
cd ../gentest && dotnet run              # замеры и картинки
```

`nuget.config` нужен: без него сборка лезет в сеть и падает.

## 3.3. Из чего состоит

```
godotcheck/     ПРОБНИК СБОРКИ
  GodotStubs.cs   заглушки типов Godot
  stub.csproj
  src/            сюда подготовить.sh кладёт исходники

gentest/        ЗАМЕРЫ И КАРТИНКИ
  Ringgen.cs      копия построения колец без Godot
  Render.cs       отрисовка PNG без зависимостей: вид сверху,
                  вид с глаз, косой вид
  ViewAudit.cs    оценка кадра: три плана, открытость, вода,
                  кромки, слои глубины, вертикали
  Paintable.cs    пригодность к раскраске: связные пятна
  PlantProxy.cs   подобия растений из простых тел
  Morpho.cs       геоморфоны и закон Хортона
  Multi.cs        многомасштабная эрозия
  Glacial.cs      ледниковый проход (отвергнут, оставлен для истории)
  Droplets.cs     капельная эрозия (отвергнута)
  Program.cs      ЗДЕСЬ ПИШЕТСЯ ОЧЕРЕДНОЙ ЗАМЕР
```

`Program.cs` переписывается под каждую задачу — это рабочее место, а не готовая
программа.

## 3.4. Четыре проверки перед каждой выдачей

```
sh проверить_вызовы.sh <путь>       методы между слоями (три пары)
sh проверить_using.sh  <путь>       объявления пространств имён,
                                    типы библиотеки, ссылки на
                                    несуществующие типы
sh проверить_методы.sh <путь>       вызовы вида Тип.Метод(
python3 проверить_скобки.py <путь>  равновесие скобок, else без if
```

**Зачем они.** Пробник подменяет `LevelView3D` и `GameBootstrap` заглушками (они
на тысячи строк и завязаны на Godot), поэтому ошибки ВНУТРИ них проходят
насквозь. За два дня это дало восемь ошибок сборки подряд.

**Каждая проверка проверена на настоящей ошибке**, а не на выдуманной. Это
обязательное условие: молчащая проверка хуже отсутствующей.

**Что проверками НЕ закрывается** и остаётся за сборкой в Godot:

- неверные имена полей (`start.Z` у `Vector2`, где составляющие X и Y);
- вызовы удалённых методов внутри файла — не отличить от доводов-функций.

Попытку собрать настоящий `LevelView3D` в пробнике я делал: не хватило шести
типов, добавил, затем вылезли `Viewport`, `SubViewport`, `RenderingServer`,
`ToSignal` и далее. Отвергнуто: дописывать заглушки для десятков систем движка —
значит поддерживать копию движка, и она разойдётся молча.

# ЧАСТЬ 4. ДОГОВОРЁННОСТИ

## 4.1. О работе

1. **Разбор идёт по логам и замерам, а не по снимкам.** Снимок показывает кусок
   под одним ракурсом, числа — весь уровень.
2. **Но: иногда лучше один раз увидеть, чем сотни раз рассчитать.** Если
   результат можно изобразить хотя бы упрощённо — надо изобразить. Отрисовщик на
   .NET нашёл вертикальные пластины, диагональную разлиновку и дюны, которых
   числа не показывали.
3. **Каждый этап конвейера должен доказать свой вклад замером.** Три этапа
   обработки колец не доказали и убраны.
4. **Каждая правка сопровождается замером до и после.**
5. **Если ответ есть в первоисточнике, не искать его во вторичном.** Я просил
   снимки из мобильных игр-раскрасок, имея под рукой сотни репродукций живописи.
6. **Пользователь не проверяет то, что можно проверить на стенде.** Прогон в
   движке — для приёмки, не для отладки.

## 4.2. О коде

7. **Пояснения на русском, по существу: не «что», а ПОЧЕМУ так.** С числами
   замеров, с описанием отвергнутых вариантов.
8. **Никаких английских терминов там, где есть русские.**
9. **Формат архива:** каталог верхнего уровня, изменившийся целиком. Плюс файл
   «ЧТО_В_АРХИВЕ.txt» с разбором сделанного.
10. **Метка сборки меняется с каждой выдачей** — по ней видно, какая версия
    реально лежит на диске.
11. **НЕ КЛАДИ `.cs` в `tools/`** — Godot собирает все `.cs` под корнем.

## 4.3. О порядке

12. **Сперва мера, потом подгонка.** Иначе упираешься в число, которое растёт,
    пока картинка портится.
13. **Мера восприятия заводится ВМЕСТЕ с мерой правильности, а не после.**
14. **Мера красоты НЕ ЗАМЕНЯЕТ меру правдоподобия.** Одна уводит в дюны, другая
    в непроходимую гофру. Подгонять по обеим сразу.

# ЧАСТЬ 5. ПРИНЦИПЫ РЕФАКТОРИНГА

Чек-лист, проверять при каждом разборе:

1. **Величина, назначенная под старую беду, живёт дальше и создаёт новую.** Юбка
   опускалась на 600 м под стык, исправленный тридцатью сборками ранее.
   *Проверять: не потеряли ли смысл прежние запасы.*

2. **Одно понятие, вычисляемое в двух местах, рано или поздно расходится.**
   Десять задвоений за проект.

3. **Величина, снятая на глаз с одного мира, ломается при смене миров.**

4. **Ни одного `new` на массив в цикле, который идёт сотни раз.** 92 МБ мусора
   за построение → 9.6 МБ.

5. **Структура крупнее 16 байт — через `in`.**

6. **Прежде чем править то, что рисует, — убедиться, ЧЕМ оно рисуется.**

7. **Узор мельче грани превращается в шум.** Пять случаев.

8. **Каждый этап должен доказать вклад замером.**

9. **Если правка верна по замерам, но на картинке ничего не изменилось —
   проверять не саму правку, а доходит ли её выход.** Восемь случаев подряд с
   остатками старого генератора: механизм считает, выход не доходит.

10. **Если проверенный инструмент не даёт результата — либо он применяется
    неверно, либо неверно понят предмет.** Гладкие купола три захода чинили
    эрозией, а это были замкнутые впадины.

11. **Прежде чем считать зависимость неразрешимой, посчитать, ЧТО именно из неё
    берётся.** Старый генератор держала ОДНА постоянная; я отложил удаление на
    заход, а работы оказалось на двадцать минут.

12. **Если стенд и игра расходятся на порядки — разница в них самих, а не в
    данных.** Расстановка: 15 мс на стенде, 65 850 в игре.

13. **Мера, зависящая от разрешения или радиуса измерения, сравнима только при
    одинаковых настройках.** Тринадцать случаев обманувшей меры.

# ЧАСТЬ 6. ЛИТЕРАТУРА И ЧТО ИЗ НЕЁ ВЗЯТО

## 6.1. Композиция и живопись

**Edgar Payne, «Composition of Outdoor Painting»**
Пятнадцать композиционных схем явным списком. Взято: безмен (главная масса у
точки опоры), круг (господствующий просвет), сложная кривая S — «применима при
изображении рек, дорог, оврагов, видимых с высокой точки», то есть прямо наш
ракурс шара. Отвергнуты как непригодные для пленэра: крест, весы.

**John Carlson, «Guide to Landscape Painting»**
ЧЕТЫРЕ ПЕРВИЧНЫЕ ПЛОСКОСТИ и их тона:
```
небо                  самое светлое
плоская земля         светлое      — смотрит прямо в небо
наклонная (горы)      средне-тёмное
вертикальная (деревья) самое тёмное
```
Порядок неочевиден: **земля светлее гор**. Диагноз проекта: у нас было ДВЕ
плоскости из четырёх, обе средние.

**Kevin Macpherson, «Landscape Painting Inside and Out»**
ЧЁРНО-БЕЛЫЙ ПЛАН: сцена делится на две формы — свет и тень; светлые формы
СОЕДИНЯЮТ между собой, и то же с тёмными. Взято как мера пригодности к раскраске
(`Paintable.cs`). Плюс: «контур формы сообщает свойства предмета, а не то, чем
она залита» — оправдание подобий растений из простых тел.

**Zoltan Szabo, «Landscape Painting in Watercolor»**
ПРИЩУР: размытие перед сведением к тонам. Без него мелкая рябь даёт сотни пятен
там, где глаз их не видит. Взято в `Paintable.cs`.

**Michael Freeman, «The Photographer's Eye»**
Три плана. Про вид сверху: «в них часто недостаёт свидетельства самой точки
съёмки» — это диагноз нашего шара. Про равновесие: «глаз тянется к светлому».

**Galen Rowell, «Mountain Light»**
КРОМКИ: «самое интересное в природе — кромки: где океан встречает сушу, луг
встречает лес, граница леса касается высот». Взято в меру кадра — у нас кромки
есть в 77-98% кадров, то есть тут всё хорошо. Плюс разведение тёплого солнца и
холодной тени: было 0.02 по синеве, стало 0.17.

**Edward Kemp, «Landscape Gardening» (1850-е)**
Третий независимый источник о трёх планах, но сильнее: **передний план надо
СОЗДАВАТЬ рядом с точкой обзора**, если его нет. И: растительность ставится
нарочно, чтобы ОБРАМЛЯТЬ вид. Не применено, записано.

## 6.2. Предпочтения пейзажа

**Kaplan & Kaplan, «The Experience of Nature»**
Матрица предпочтения: связность, сложность, читаемость, тайна. Сложность не
должна быть ни малой, ни большой. «Деревья, размечающие глубину» — признак
предпочитаемых сцен. Связности и сложности нужен минимум; читаемости и тайны —
чем больше, тем лучше.

**Jay Appleton, «The Experience of Landscape»**
Обзор, укрытие и ОПАСНОСТЬ. Формула Лоренца: «видеть, не будучи увиденным».
Третье понятие не применено: требует растительности и скал ближнего плана.

**Herzog, измерения предпочтений** (через обзоры)
```
горные виды с водой   3.99   <-- НАША ИГРА
крупные водоёмы       3.28
реки, озёра           3.11
болота                2.13
```
Вода — сильнейший отдельный элемент из всех измеренных.

## 6.3. Геоморфология

**Horton (1945), порядок Стралера**
Отношение числа русел соседних порядков у настоящих рек 3-5. Случайная рябь
этому не подчиняется. Взято в `Morpho.cs` и в отчёт игры. У нас 4.2-4.5 — сеть
правдоподобна.

**Геоморфоны (Jasiewicz & Stepinski), основа меры PTRM**
Десять видов форм и их доли. Природное распределение для гор:
```
вершина 2, гребень 8, плечо 10, отрог 15, склон 38,
лощина 15, подножие 8, долина 4, яма 0
```
Взято в `TerrainMetrics.cs` — это главная мера правдоподобия рельефа.

**«Geomorphology from Space» (Short, NASA)**
Дала разгадку замкнутых впадин: изрезанность наших была 1.31-1.42 (почти круг),
у горных озёр 2-4 (вытянуты по долине). Круглая впадина бывает от провала,
взрыва или выдувания — значит артефакт счёта.

**«Global Mega-Geomorphology» (NASA CP-2312, 1985)**
Понятие ПОРОГА: «существуют граничные условия, за которыми начинают преобладать
иные процессы». Плюс предостережение: региональная геоморфология «должна
сосредоточиваться не на подробностях, а на множественности процессов».

**Schott и др., врез по силе потока**
«Сходится к установившемуся состоянию за несколько секунд». Это опровергло нашу
настройку: поле останавливалось на 157 итерациях из нужных 450.

**Davis (1909), схема ледниковой переработки**
Ледник НЕ строит рельеф заново, а ПЕРЕРАБАТЫВАЕТ готовый речной. Цирки, ареты,
троги. Проход написан и **отвергнут по замеру** — см. 7.3.

# ЧАСТЬ 7. ЧТО ПРОВЕРЕНО И ОТВЕРГНУТО

Это важнее списка сделанного: не повторять.

## 7.1. Капельная эрозия
```
вариант          уклон  спектр 60м  ям    время
без правки       29.3°     100      30      —
засыпка впадин   28.7°     102       0     6 мс
капли            28.3°      88       0  1001 мс
```
Капли СРЕЗАЮТ подробность и стоят в 170 раз дороже. Единственную пользу —
устранение ям — даёт засыпка впадин.

## 7.2. D-бесконечность
Проверена дважды: на грубом поле (2.88x→2.48x, диагонали без изменений) и на
мелкой сетке (расчленение 12.7→7.8). Размазывает врез.

## 7.3. Ледниковый проход

# ЧАСТЬ 8. ГРАБЛИ, НА КОТОРЫЕ Я НАСТУПАЛ

Тринадцать случаев обманувшей меры и восемь поломок от старого генератора. Самое
поучительное:

**Мера растёт, а картинка портится.** «Смен знака склона на километр» считала
любую рябь. Заменена на геоморфоны и Хортона.

**Мера зависит от разрешения.** `aspectBias` давал 1.37x при ячейке 480 м и
4.04x при 15 м на ОДНОМ И ТОМ ЖЕ рельефе.

**Мера зависит от числа лучей.** Оценка вида: 12% при 24 лучах, 50% при 64.

**Мера считала по выдуманным порогам.** Я взял пороги поясов наугад, а игра
считает их квантилями. Замер врал вдесятеро.

**Правка применилась, но выход не дошёл.** Восемь раз: лента воды красилась не
тем материалом; растительность лежала в чужих координатах; выбор места давал
центр карты; высота бралась из пустой сетки; флажок глушил растительность; выход
по числу областей обрывал построение.
