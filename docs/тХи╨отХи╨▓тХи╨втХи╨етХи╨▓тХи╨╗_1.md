## 6. Куда делся поток в кольцах

**Проверил по коду. Перенос НЕ БЫЛ НАПИСАН НИКОГДА.**

**Что делать.** Заполнять `ringFlow` выборкой из дренажа при построении каждого

## 7. По какой высоте нормируется расстановка растений

**Задвоение, и оно моё.** Проверил оба места.

**Пояса колец** (`FarBackground.cs:410–444`): `heightSamples` собираются
перебором **дренажной сетки** (`for j = 0; j < DrainageSide; j += 2`), затем
`new BeltThresholds(heightSamples)` — квантили по этой выборке.

**`BiomeAtWorld`**, которым питается расстановщик: пределы `lo2`/`hi2` берутся
перебором **всего поля `_fluvial`** — наименьшее и наибольшее, а не квантили.

То есть **одно понятие считается двумя способами**: пояса по квантилям одной
выборки, растительность по размаху другой. Расхождение неизбежно.

**Это второй пункт чек-листа рефакторинга:** «одно понятие, вычисляемое в двух
местах, рано или поздно расходится». Десять случаев за проект, это одиннадцатый.

**Что делать:** `BiomeAtWorld` должен спрашивать те же `_belts`, что и кольца, и
нормировать по тем же пределам. Правка на несколько строк.

**Про вашу арифметику с 3703 м.** Она подтверждает диагноз: по полю точка выше
скалы, по нулевому кольцу — лес. Сосняк на снимках означает, что расстановщик
взял свою нормировку, а покров — свою.

## 8. Два счётчика шпилей

**Считают разное, и оба верны в своих границах.**

`[рельеф] шпилей 0` — из отчёта о мешe, считается по **готовому мешу** и ищет
вырожденные треугольники и торчащие вершины. Ноль здесь означает, что меш
геометрически цел.

`terrain.json spikes 301` — из `TerrainMetrics.PitsAndSpikes`, считается **по
сетке высот кольца** и ищет узлы, отличающиеся от всех соседей больше чем на
порог в метрах.

**Имелось в виду второе.** Триста один шпиль на дальнем кольце при ячейке 480 м —
это узлы, торчащие на 200 м над соседями, и они настоящие: дальнее кольцо у нас
худшее по всем мерам (отклонение форм 51–52).

**Первый счётчик стоит переименовать**, чтобы не путались: он про целость меша,
а не про рельеф.

## 9. К чему привязывать целевые числа из репродукций

**Целевые числа сняты способом, близким к `[кадр]`, а не к `[sketch]`.**

Точный порядок, которым я мерил 60 репродукций:

```
1. изображение → яркость (среднее по трём составляющим)
2. уменьшение до 320×180
3. размытие: два прохода по окну 3×3      ← «прищур» по Szabo
4. сведение к трём тонам ПО КВАНТИЛЯМ яркости
5. связные пятна по четырём соседям
6. «сор» = пятна мельче сотой доли кадра
```

Это ровно то, что делает `[кадр]`. Оттуда медиана 10, крупнейшее 29%, сор 13%.

**Переносить на `[sketch]` нельзя.** Он работает по служебным проходам —
опознаватель, глубина, нормаль, — и режет кадр по другому признаку: не по тону, а
по предмету и форме. Расхождение 45% против 3% на одном кадре это и показывает.

**Что делать.** Либо мерить эталон способом `[sketch]` — то есть прогнать
репродукции через тот же разбор, что невозможно (у картин нет проходов
опознавателя), — либо **признать `[кадр]` мерой пригодности, а `[sketch]`
считать отдельной величиной** про механику раскраски.

Я склоняюсь ко второму: `[sketch]` отвечает на вопрос «сколько областей получит
игрок», `[кадр]` — «похож ли кадр на картину». Это разные вопросы, и эталон нужен
свой для каждого.
